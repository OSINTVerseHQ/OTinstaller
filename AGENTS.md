# otinstaller: project rules

## What this is
otinstaller is a Python CLI, distributed on PyPI, that installs, runs, updates and
removes open-source command line tools by name, using one standard command interface.
It is a neutral tool manager, similar in spirit to pdtm, pipx or Kali's tool packages.
Tool descriptions, docs and messages stay neutral.

## Fixed decisions (do not change without asking)
- Package and command name: otinstaller.
- The word "OSINT" must not appear in the package name, command name or CLI help text.
  It may appear in the README and the PyPI description only.
- Python 3.10+. Linux only. Tested on Ubuntu 22.04 and 24.04 with Python 3.10, 3.11, 3.12.
- Managed tools are installed with pip or git only. No Go, Rust, Node or Docker.
- Every managed tool gets its own virtualenv. Never install tools into system Python.
- Run command shape: `otinstaller run <tool> -- <args>`. Arguments pass straight through.
- Results are saved automatically to ./results/<tool>/<target>/ using the filename
  pattern <YYYYmmdd-HHMMSS>_<tool>_<target>_<runid>.<ext> plus a .meta.json sidecar.
  The results directory can be overridden with --output or OTINSTALLER_RESULTS_DIR.
- One env file holds all API keys: ~/.otinstaller/.env, permissions 600. Each tool only
  receives the keys it declares in its registry entry.
- Home directory is ~/.otinstaller/ (override with OTINSTALLER_HOME).
- The registry is generated by a pipeline. A tool is listed only if it passes an
  automated install test and a smoke test (--help or --version exits cleanly).
- Resume: job state lives in SQLite. Finished jobs are skipped on resume and partial
  output is always kept.
- No telemetry. Network access only to GitHub, PyPI and the registry host.

## Inclusion policy
- A tool is listed if it passes install and smoke tests and is not in the denylist.
- The denylist excludes attack or harassment tooling by capability (phishing kits, IP
  grabbers, message or call bombers, credential brute-forcers, private-account bypass,
  dox-dump hosting) and non-OSINT active scanners. It lives in registry/denylist.yaml
  and can be edited without code changes.
- Registry entries carry a `capabilities` list. Tools tagged `dual-use` require the
  responsible-use notice to be accepted before install.
- The generated list gets a human review before each release.

## Code rules
- Stack: Typer and Rich for the CLI, PyYAML, and the standard library (sqlite3,
  subprocess, asyncio, pathlib). Keep dependencies minimal. Ask before adding any.
- Layout: src/otinstaller/, tests/, docs/, registry/, pipeline/.
- The CLI layer stays thin. Real logic lives in importable modules so a TUI could
  reuse it later.
- Type hints on all function signatures. Lint and format with ruff. Test with pytest.
- Write the test first, then the code. Every feature needs tests, including failure cases.
- Never use shell=True. Pass argument lists to subprocess. Validate tool names and
  targets: no path traversal, no shell metacharacters in filenames.
- Never log or write API key values anywhere (logs, meta.json, error messages).
- Metadata is neutral: author "otinstaller contributors". No personal names, emails or
  local paths anywhere in the repo.

## Style rules (the code should read like an experienced developer wrote it)
- Comments explain why, not what. Skip comments on obvious code. Most functions need
  no docstring; add a one-line docstring only where the purpose is not clear from
  the name.
- No emojis anywhere: code, comments, README, commit messages, CLI output.
- No decorative banners, ASCII art, section divider comments, or "generated by" notes,
  except the single startup banner in src/otinstaller/banner.py (shown only on a TTY,
  never with --json or when OTINSTALLER_NO_BANNER is set).
- Do not mention AI, assistants or prompts in any file.
- Keep functions short and names plain. Prefer simple code over clever code.
- README and docs are written in plain, direct English. No marketing filler, no
  bullet-point overload, no exclamation marks.
- Commit messages are short and lowercase, imperative mood, for example
  "add config module" or "fix path handling in results".

## Workflow
- After every task run: ruff check ., ruff format --check ., pytest. Report the real output.
- If a check fails, fix it. If it still fails after 3 attempts, stop and report the
  problem instead of continuing to change things.
- Make small commits after each working step. Never leave the repo broken.
